# ChronoDesk Performance

ChronoDesk is a small desktop utility, so performance work should remain evidence-driven. The product should feel immediate while idle CPU, allocations, disk writes, and startup work stay proportionate to a clock application.

## Performance budgets

These are engineering targets for release review, not fabricated benchmark results.

### Idle clock

Target on a typical supported desktop after startup:

- no network traffic generated by ChronoDesk clock logic;
- no settings disk write on normal display ticks;
- no growing collection or log activity during ordinary successful ticks;
- stable memory after normal UI warm-up;
- clock display should not visibly miss whole seconds under ordinary system load.

### Startup

Target behavior:

- load one small settings document;
- enumerate system timezones once;
- construct the UI without fake delay;
- perform no remote initialization;
- show safe defaults when local settings are unreadable.

No hard millisecond target is claimed until representative Windows/macOS/Linux measurements are captured from release builds.

### Settings I/O

Settings documents are capped at 2 MiB, though normal files should be far smaller. Writes occur only on explicit preference/onboarding/import/reset actions, not continuously.

### World clocks

ChronoDesk caps stored world-clock cards at 24. A tick performs one timezone conversion/formatting operation per visible saved card. At this bounded scale, list virtualization is unnecessary; adding virtualization should follow evidence of a real UI cost rather than architectural fashion.

## Current hot path

The display timer runs every 250 ms so the application can refresh promptly and reliably observe an exact chime-boundary second.

Tick path:

```text
TimeProvider.GetUtcNow
  -> format local snapshot
  -> update <=24 world-clock snapshots
  -> evaluate chime policy
  -> optional playback only at a valid boundary
```

The tick path intentionally does **not**:

- read/write settings;
- enumerate the timezone database;
- perform network calls;
- scan the filesystem;
- launch a process unless an enabled chime actually reaches a cadence boundary.

## Allocation guidance

Formatting strings necessarily creates small short-lived values. Before replacing clear formatting code with pooling/caching complexity:

1. profile a release build;
2. isolate the actual allocation source;
3. measure the proposed change;
4. keep the change only if it produces a meaningful result without damaging correctness/localization.

Timezone/date correctness is more important than eliminating a tiny allocation in an already bounded path.

## Timezone catalog

`SystemTimeZoneCatalog` snapshots and sorts timezone descriptors once at construction. Search operates on that in-memory list and returns at most 200 items, with the UI asking for 60.

A runtime timezone update becomes visible after application restart. This avoids a background watcher/polling loop whose cost and cross-platform behavior would not be justified for this utility.

## Persistence reliability versus speed

`JsonSettingsStore` favors safe writes:

1. serialize to a unique temporary file;
2. flush;
3. replace/move to the requested path;
4. remove a leftover temporary file when needed.

For a small user-triggered settings document, reliability is more important than shaving an unmeasured fraction of a millisecond from the write.

## Logging

Successful clock ticks are not logged. This avoids continuous disk growth and unnecessary I/O.

The active JSONL log rotates near 1 MiB. Error reporting itself is best-effort and must not crash the clock when logging storage is unavailable.

## UI layout

Main layout uses a bounded number of clock cards and scrollable sections. Performance review should watch for:

- excessive layout invalidation when clock text width changes;
- very large font sizes causing repeated expensive reflow;
- expensive effects/shadows introduced by future styling;
- unnecessary animation at every tick;
- image assets much larger than displayed size.

The current design deliberately avoids fake skeleton delays and decorative clock animations.

## Measurement procedure

When a release candidate can be run on a real desktop, capture:

- OS/version/architecture;
- release commit/tag;
- self-contained vs framework-dependent build;
- number of world clocks;
- theme/layout/font size;
- startup time observation/tool;
- idle CPU sample over at least several minutes;
- working set/private memory after warm-up;
- allocations/GC rate if a profiler is available;
- behavior during focus and mini modes.

Use platform-appropriate profilers such as Visual Studio diagnostics, `dotnet-trace`/`dotnet-counters` where applicable, Instruments on macOS, or a trustworthy system profiler on Linux.

## Regression threshold

Treat a change as performance-sensitive when it introduces one of the following without a documented reason:

- continuous disk/network activity while the clock is idle;
- a new background polling loop;
- unbounded collection growth;
- visibly missed seconds under normal load;
- major startup work unrelated to initial rendering/settings/timezones;
- material CPU/memory regression confirmed by the same measurement method.

Fix correctness bugs first when a proposed optimization would make timezone, chime, localization, or accessibility behavior less reliable.

## Future benchmark code

A dedicated benchmark project is appropriate only when there is a hot path worth comparing across commits. If added, keep benchmark packages isolated from production projects and do not make microbenchmark output a substitute for real desktop profiling.
