# ChronoDesk Performance

ChronoDesk is a small cross-platform clock utility, so performance work should remain evidence-driven. The product should feel immediate while idle CPU, allocations, storage writes, battery impact, browser main-thread work, and startup work stay proportionate to a clock application.

## Performance budgets

These are engineering targets for release review, not fabricated benchmark results.

### Idle clock — all hosts

Target after startup:

- no network traffic generated by ChronoDesk clock logic itself;
- no settings write on normal display ticks;
- no growing collection or log activity during successful ticks;
- stable memory after normal UI/runtime warm-up;
- clock display should not visibly miss whole seconds under ordinary host load;
- no duplicate timers after mobile lifecycle detach/reattach;
- no unnecessary background work after `MainView` detaches from the visual tree.

### Desktop

Additionally target:

- low idle CPU across normal/focus/mini modes;
- no continuous tray/startup/chime polling;
- no process launch except when an enabled desktop chime reaches a valid cadence boundary.

### Android / iOS / iPadOS

Additionally target:

- timer lifecycle stops when the single-view surface is detached;
- rotation/resume does not create duplicate tick loops;
- bounded allocation/layout work on phone/tablet sizes;
- no desktop process/tray/startup work in the mobile host.

Battery-impact claims must not be made without device measurements.

### Browser / WebAssembly

Additionally target:

- bounded main-thread/layout work;
- no repeated runtime/network fetches caused by clock ticks;
- no assumption that browser virtual filesystem operations are equivalent in cost/persistence to native storage;
- responsive behavior at narrow and wide viewports.

Browser-host startup necessarily downloads/loads application and .NET WebAssembly assets from the hosting origin; that delivery cost is distinct from recurring clock logic.

## Startup target behavior

All hosts should:

- create the small shared service graph;
- load one small settings document/runtime-store representation where available;
- enumerate runtime timezones once;
- construct the appropriate UI lifetime without fake delay;
- perform no ChronoDesk backend/account initialization;
- show safe defaults when local settings are unreadable/unavailable.

No hard millisecond target is claimed until representative measurements are captured from real release builds/devices/browsers.

## Settings I/O

Settings documents are capped at 2 MiB, though normal files should be far smaller. Writes occur only after explicit preference/world-clock/onboarding/import/reset changes, not continuously.

Native filesystem-backed writes favor reliability over micro-optimization. Browser storage/runtime filesystem behavior must be measured separately rather than inferred from desktop disk timing.

## World clocks

ChronoDesk caps saved world-clock cards at 24. A tick performs one timezone conversion/formatting operation per visible saved card. At this bounded scale, introducing virtualization/caching complexity should follow evidence of a real performance problem on representative hosts.

## Current hot path

The display timer runs every 250 ms so ChronoDesk can refresh promptly and reliably observe an exact chime-boundary second.

Shared tick path:

```text
TimeProvider.GetUtcNow
  -> format local snapshot
  -> update <=24 world-clock snapshots
  -> evaluate chime policy
  -> optional playback only when host/cadence supports it
```

The tick path intentionally does **not**:

- read/write settings;
- enumerate the timezone database;
- perform ChronoDesk network calls;
- scan the filesystem;
- launch a process unless an enabled supported desktop chime actually reaches a cadence boundary.

`MainView` guards against overlapping tick execution and stops its timer on visual-tree detachment.

## Allocation guidance

Formatting strings creates small short-lived values. Before replacing clear formatting code with pooling/caching complexity:

1. profile the affected host in Release configuration;
2. isolate the actual allocation source;
3. measure the proposed change;
4. compare the same scenario before/after;
5. keep the change only when it produces a meaningful result without damaging correctness, localization, accessibility, or platform compatibility.

Timezone/date correctness is more important than eliminating tiny allocations in an already bounded path.

## Timezone catalog

`SystemTimeZoneCatalog` snapshots/sorts timezone descriptors once at service construction. Search operates on the in-memory list and returns a bounded result set, with the UI normally asking for 60.

A runtime timezone update becomes visible after application restart/reload. This avoids adding a background watcher/polling loop whose cross-platform cost/behavior is not justified for the current utility.

## Persistence reliability versus speed

On compatible native filesystem hosts, `JsonSettingsStore` favors safe writes:

1. serialize to a unique temporary file;
2. flush;
3. replace/move to the requested path;
4. remove leftover temporary data when needed.

For a small user-triggered settings document, reliability is more important than shaving an unmeasured fraction of a millisecond.

WebAssembly uses sandboxed runtime storage/filesystem semantics; native atomic-file performance/behavior must not be assumed there without deployment testing.

## Logging

Successful clock ticks are not logged. This avoids continuous storage growth and unnecessary I/O.

The active filesystem-backed JSONL log rotates near 1 MiB. Error reporting is best-effort and must not crash the clock when logging storage is unavailable/sandboxed.

## UI layout

The shared UI uses a bounded number of clock cards and scrollable sections. Performance review should watch for:

- excessive layout invalidation when time text width changes;
- very large font/text-scaling values causing expensive reflow;
- expensive effects/shadows introduced by future styling;
- unnecessary animation at every tick;
- images much larger than displayed size;
- repeated re-layout during device rotation;
- browser resize/zoom thrashing;
- inaccessible optimization techniques such as suppressing necessary text updates.

The current design deliberately avoids fake skeleton delays and decorative clock animations.

## Measurement matrix

When a release candidate can run on real targets, capture representative evidence rather than extrapolating one desktop measurement.

### Desktop record

Capture:

- OS/version/architecture;
- release commit/tag;
- RID/build mode;
- world-clock count;
- theme/layout/font size;
- startup observation/tool;
- idle CPU over several minutes;
- working set/private memory after warm-up;
- allocations/GC rate when available;
- focus/mini behavior.

Use platform-appropriate tools such as Visual Studio diagnostics, `dotnet-trace`/`dotnet-counters`, Instruments, or trustworthy OS profilers.

### Android record

Capture:

- device/emulator/API level/ABI;
- Release vs Debug;
- startup observation;
- memory/CPU after warm-up;
- lifecycle resume/rotation behavior;
- battery/energy data only when measured with a suitable tool.

### iOS / iPadOS record

Capture:

- simulator/device model + OS;
- architecture;
- Release vs Debug;
- Instruments measurements where available;
- lifecycle/orientation behavior;
- energy/battery observations only when measured.

### Browser record

Capture:

- browser/version + OS/architecture;
- published Release site;
- initial transfer/load size and startup timing using browser developer tools;
- main-thread/CPU profile during idle ticking;
- memory after warm-up;
- narrow/wide viewport behavior;
- reload/storage behavior.

## Regression threshold

Treat a change as performance-sensitive when it introduces one of these without a documented reason:

- continuous disk/network/storage activity while idle;
- a new background polling loop;
- duplicate timer after lifecycle transitions;
- unbounded collection growth;
- visibly missed seconds under normal load;
- major startup work unrelated to application/runtime loading, settings, timezones, or initial rendering;
- material CPU/memory/energy regression confirmed by the same measurement method;
- browser main-thread work that makes basic interaction/scrolling visibly unresponsive.

Fix correctness bugs first when an optimization would make timezone, lifecycle, chime policy, localization, accessibility, persistence, or platform behavior less reliable.

## Future benchmark code

A dedicated benchmark project is appropriate only when there is a hot path worth comparing across commits. Keep benchmark packages isolated from production hosts and do not use microbenchmark output as a substitute for real desktop/device/browser profiling.
